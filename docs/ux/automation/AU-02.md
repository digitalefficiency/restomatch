# AU-02 · Intake truth: supplier from the printed ח״פ, consolidated invoices reach finance, stuck reads recover
**One line:** an invoice that arrives without a known supplier gets one proposed from its own printed ח״פ, a one-tap confirm instead of a dropdown. A real חשבונית מרכזת is announced to finance as a neutral (T4) "proposal ready", never matched as a false leak. A read stuck past the signed-URL window is re-signed and retried once instead of waiting for a human.

Today:
- the OCR reads the ח״פ, but nothing maps it to a supplier (int-01 §5);
- a supplierless invoice escapes number-dedupe (NULLs never collide);
- the consolidated proposal returns null without a supplier (`match/consolidated.ts:1043`);
- `ocr_pending` older than 25 minutes is left for an ops e-mail (`ocrSweep.ts:9-14`).

Hours: ≈80 documents/month (ASSUMPTION, spec §1). The supplier pick drops from 2–3 taps to 1 on the share that arrives supplierless (ASSUMED 20–40%, to measure in AU-07), and stuck reads stop needing a resend. Catalogue A8 + A9 + A10: 0.16–0.55 h/week ≈ **₪70–230/month hours-₪** (sum of the three rows, overlaps not netted; shown apart from leak ₪). ₪ protected: consolidated spend stops being shown as false leak (lab: ₪3,603 consolidated spend sits outside the leak today). ## 5. Acceptance criteria
1. **Supplier suggestion (A8).** After a successful read with `invoice.supplierId === null` and a valid printed ח״פ (`isValidIsraeliBusinessId`), `suggestSupplier()` finds exactly **one** active supplier of this restaurant whose `normalizeBusinessId(business_id)` equals it.
   - It writes `raw.supplierSuggestion = { supplierId, basis: 'business_id', printed }` (merged into `raw`, never replacing it).
   - Zero or 2+ matches → no suggestion, plus the review reason `supplier_unknown`.
   - The invoice stays `parsed` (review) and is **never auto-matched** without a supplier.
2. **The dead check revived.** When `supplierId` is known before the read (receiving path, linked sender), the pipeline gets `expectedSupplierBusinessId`, or train B's `supplierBusinessIdMismatch` already covers it (then add only a test that it fires on a mismatch and not on a missing ח״פ).
3. **`ingest.setInvoiceSupplier`** (`managerProcedure`; G-07 `can('intake.approve')` once merged; bookkeeper per W2-02 decision).
   - Input `{ invoiceId, supplierId, expectedSupplierId: null, clientMutationId }`.
   - It checks that the supplier and the invoice are this restaurant's and that the invoice's supplier is still NULL (a guarded `UPDATE … WHERE supplier_id IS NULL`, else CONFLICT naming who set it).
   - **Dedupe:** if `(supplierId, invoice_number)` already exists, the unique index would throw. It catches that and leaves `supplier_id` NULL, writes `raw.duplicateOf = {invoiceId, invoiceNumber}` and the review reason `duplicate_number`, and returns `{ duplicateOf }`. The UI shows "מספר חשבונית כבר קיים אצל הספק · בדקו לפני אישור".
   - On success: one audit row `intake.supplier_set` (`automationId: 'A8'`, `basis: 'suggestion' | 'manual'`). If the read had no other review reason, `enqueueMatchInvoice` runs after commit (same rules as `ocrMayAutoMatch`). `ocrMayAutoMatch` lives in the worker today (`apps/worker/src/jobs/ocrInvoice.ts:626`) and packages/api cannot import from an app, so AU-02 **moves** the decision into `packages/api/src/ingest/autoMatch.ts` (exported from the root) and `ocrInvoice.ts` imports it from there (both files are in AU-02's boundary).
