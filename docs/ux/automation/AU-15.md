# AU-15 · Learn from decisions: when the owner keeps waiving the same price, propose making it the contract price
**One line:** when the owner or manager has marked the same supplier's price for the same product as "מחיר מוסכם" three times, RestoMatch proposes recording it as a contract price: "3 פערים נסגרו ידנית כ'מחיר מוסכם' · לקבוע ₪42.00 לק״ג כמחיר חוזה מ-01.12?". The owner accepts it once, and future **orders built through the order guide** (W2-06 `resolveExpectedPrice`, contract first) carry the agreed price, so their invoices stop raising the alarm. A contract is a **ceiling** on the PO's expected price (`contracts/load.ts:77-81`): a captured, platform-imported or hand-typed PO that carries its own lower price still raises PRICE_HIGHER, and the card says so.

The same loop proposes a catalog unit or product fix when the same OCR line is corrected again and again (once corrections are recorded). Nothing changes the engine, no tolerance widens, and the owner signs every rule.

Today:
- every waive writes `after.reasonCode` (`routers/approvals.ts:427,454`), and nothing reads it (the code comment names "the H6 learning loop", `approvals.ts:65-67`);
- the same agreed price raises the same PRICE_HIGHER on every invoice;
- line corrections are not audited at all (`audit.ts:33-60` has no correction action).

Impact (catalogue A20, ASSUMPTIONS): manager/owner 0.04–0.12 h/week (10–30 repeat waives a month at ~1 min) ≈ **₪20–55/month hours-₪**. Money-₪: **none**. The value is fewer false alarms and a leak number the owner keeps believing (North Star "that one owner believes").

## 5. Acceptance criteria
1. **The rule (`suggestions/contractPrice.ts`).** `contractPriceSuggestions(db, rid, now)` reads `audit_log` rows with `action = 'discrepancy.rejected'` and `after->>'reasonCode' = 'price_agreed'` from the last 120 days, joined to their discrepancy (`type = 'PRICE_HIGHER'`, `product_id` not null) and the invoice's supplier. It groups by (supplier, product, **PO unit**): the unit comes from `po_lines.unit` through `discrepancies.po_line_id` (the `discrepancies` table has no unit column, and for PRICE_HIGHER the engine stores `actual_value` = the billed price **normalised to the PO line's unit**, `invPrice = unitPriceBilled / unitFactor`, `engine.ts:240-244, 313-315`). A waive without a `po_line_id` is skipped. A suggestion needs all of:
   - **K ≥ 3** distinct invoices (a named constant `SUGGEST_AFTER_WAIVES = 3`);
   - the waived `actual_value` unit prices within ±2% of their median;
   - no contract in force today for (supplier, product) at a price ≥ that median;
   - not dismissed in the last 90 days (audit `suggestion.dismissed` with the same key);
   - the latest waive was not reopened (`approvals.reopen`) after the fact.
   The suggested price = the median, in integer price units (scale 4), with the range shown. Key = `cp:<supplierId>:<productId>:<poUnit>`. Accept passes that PO unit to `contracts.create`; `contractPriceInUnit` is used only when comparing to an existing contract recorded in another unit.
2. **Reads.** `suggestions.list()` (owner + manager; interim `managerProcedure`; bookkeeper read-only is allowed) returns `{key, kind: 'contract_price', supplierName, productName, unit, priceUnits, min, max, waives: [{invoiceNumber, date, discrepancyId}], since}`. Receiver and chef → FORBIDDEN.
3. **Accept (owner only).** `suggestions.acceptContractPrice({key, contractPrice, unit, validFrom, clientMutationId})` (`ownerProcedure`):
   - it re-evaluates the rule server-side (a stale key → CONFLICT "ההצעה כבר לא בתוקף");
   - `validFrom` ≥ today (Israel day), so no back-dating; `validTo` null unless given;
   - it inserts through the same validation as `contracts.create` (the exported core helper, or `createCaller`), with `source 'manual'`;
   - it needs the `contracts` flag, else FORBIDDEN `FLAG_OFF`;
   - one audit row `suggestion.accepted` (`after: {key, contractPrice, validFrom, waives: K, automationId: 'A20'}`); a replay writes nothing new;
   - it **does not** touch any existing discrepancy, claim or match run (test: rows identical before/after) and enqueues no re-match.
   The manager sees the card read-only with "ממתין לאישור הבעלים" and may dismiss it.
4. **Dismiss.** `suggestions.dismiss({key, clientMutationId})` (owner + manager) writes `suggestion.dismissed` (A20). The card disappears for 90 days, and a new waive after that may raise it again.
5. **The card.** In W2-12's "לטיפול" queue, T4 neutral (a proposal, not a problem):
   - title "הצעה: מחיר חוזה לסלמון · דגי הים התיכון";
   - body "3 פערים נסגרו ידנית כ'מחיר מוסכם' מאז 12.10 (₪41.80–₪42.10 לק״ג) · מחיר חוזה ימנע את ההתראה בחשבוניות הבאות";
   - actions: [קבעו ₪42.00 לק״ג מ-01.12] (owner) · [לא עכשיו];
   - the price and date are editable in a `ConfirmDialog` with `MoneyInput` and `DateField`;
   - ₪ via `<Money>`. The copy never promises savings in ₪ and never says "1.5%".
6. **Correction suggestions (PR b).** When the correction audit exists, `correctionSuggestions(db, rid, now)` finds, per supplier and raw line description (or SKU), ≥3 corrections in 90 days with the same change:
   - the same `unit` from → to: "שטראוס · 'שמנת 38%': תיקנתם 4 פעמים יחידה 'יח׳' ל'ארגז' · [עדכנו בפריט הקטלוג]". The link goes to the catalog item with the unit pre-filled (`catalog.updateItem`, a human save);
   - the same `productId` from → to: "… קושרה מחדש 3 פעמים ל<מוצר> · [אשרו קישור]". This is a pre-filled `mapping.confirm` (G-08 review), never a direct alias write.
   Until then the procedure returns no correction kind. This is not an error.
7. **Server enforcement and tenancy.** Every reader filters `restaurant_id` explicitly and joins only this restaurant's invoices and suppliers. A key with a foreign supplier or product → NOT_FOUND. Receiver/chef FORBIDDEN on all three procedures (attack test).
8. **Leak safety.** On the lab: accepting a seeded suggestion leaves the hero (₪759.54), pay run and letters identical **today** (attach the output). A new invoice dated after `validFrom`, on a PO **created through W2-06 `resolveExpectedPrice`** (contract first), at the agreed price raises no PRICE_HIGHER, and one above it still does. A PO that carries its own price **below** the contract (captured, imported, hand-typed) still raises PRICE_HIGHER at the agreed price, because the contract is a ceiling (`contracts/load.ts:77-81`, rule 3); copy and KPI never claim the alarm stops for those POs (engine unchanged, tests through `runForInvoice` on fixtures). Changing ceiling-vs-floor would move leak ₪: it is out of scope here and, if wanted, a human-PR proposal to the contracts/load owner (W2-12 / G-04), noted in the PR body. The canary is green.
9. **Off switch and KPI hook.** Option `ruleSuggestions` off → `suggestions.list` returns `[]` and the card is hidden; accept/dismiss → FORBIDDEN `OPTION_OFF`. KPI: audit `suggestion.accepted|dismissed` (A20, `kind`); AU-07 reads "suggestions accepted %" and "repeat PRICE_HIGHER on accepted pairs, on POs priced through `resolveExpectedPrice`" (should fall to 0; POs carrying their own lower price are counted apart and are expected to keep alarming).

Where the docs conflict: the catalogue says "suggest a contract price **or a tolerance override**" (int-03 §10.7). Tolerances are engine-adjacent and widen what is never caught, so AU-15 proposes contract prices only. The catalogue's "owner accepts" wins over `contracts.create`'s manager tier.
