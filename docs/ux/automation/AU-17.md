# AU-17 · Supplier communication loop: one owner tap sends, the supplier's answer comes back as a proposal
**One line:** a credit letter or a 7-day reminder leaves the server to the supplier's own e-mail (PDF attached) or WhatsApp (approved template) after **one owner tap**, the claim moves to "נשלח" only when the provider confirms, and the supplier's answer ("מאשרים", "נוציא זיכוי", "לא מקובל") is captured, classified read-only, and shown as a proposal a person confirms.
- **Impact (assumption):** 4–8 letters + reminders a month at the ICP restaurant; today each costs a contact look-up, a hand-off and a return trip to "סמנו כנשלח" (int-04 §3: 4–6 taps per supplier) and replies are read in a phone nobody else sees. Time: manager ≈0.03–0.25 h/week (letters + reply reading, partly overlapping A12) ≈ **₪15–110/month time-₪** (catalogue A22). Money: ASSUMED +5–10 points of collection share on ₪1,800/month claimable ≈ **₪90–180/month recovered**, inside the recovery bundle range of A12 (not added to it). WhatsApp cost ≈ ₪0.02/message (ext-02 §0.5, since 1.10.2026). Never summed.
- **Today:** "WhatsApp" opens `wa.me/?text=` with no number and "e-mail" opens `mailto:?` with no address (`apps/web/app/dashboard/leaks/claims/letter-actions.tsx:44-45`); nothing leaves the server for a claim; a supplier's text-only WhatsApp reply is either parsed as an order or dropped as `empty`, and no message body is stored (`packages/api/src/ingest/pipeline.ts:390-425`; `schema.ts:1371-1396`).
**Owner agent:** web-feature-engineer (leak-economist signs letter/reminder wording; tenant-security-warden reviews the send mutation and the ingest hook; growth-pmm-engineer reviews supplier-facing tone). **Device:** both (send from phone or desk; replies panel on desk). **Effort:** L (3 PRs: a = e-mail send + delivery-truth; b = reply capture + classifier + proposals; c = WhatsApp templates after H-05). **humanPR:** no for this package (`outbox.ts` unchanged: attachments ride in `payload.__attachments`); it needs H-05 core (templates, reply-to), H-06 (portal answers) and H-13 (`claim_replies`, supplier opt-in).

## 5. Acceptance criteria
1. **`claimComms.send`** (owner only by default: `SEND_ROLES = ['owner']`, manager only on the owner's word; mutation). Input `{kind: 'letter'|'reminder', letterId | supplierId, channel: 'email'|'whatsapp', clientMutationId}`.
   - `letter`: the W2-10 `claim_letters` row must be `draft`/`ready` and contain only `claimed` claims; the body is its `content_snapshot` text; the PDF (`letterPdf.ts`) is attached via `payload.__attachments`.
   - `reminder`: the text is AU-03's `supplierReminderDraft` for that supplier's overdue claims (acknowledged → softer variant, AD5).
   - Target: `suppliers.reconciliation_email ?? contact_email` / `reconciliation_whatsapp ?? contact_whatsapp` (E.164 via W2-11's normaliser). No target → BAD_REQUEST `NO_SUPPLIER_CONTACT`, UI offers the wa.me/mailto hand-off instead.
   - WhatsApp also requires `suppliers.whatsapp_opt_in_at` (H-13) and a configured template; else the WhatsApp option is hidden and the server refuses `NO_OPT_IN`.
   - One outbox row, `related_entity_type 'claim_letter'|'claim_reminder'`, `dedupe_key = au:A22:<restaurantId>:<supplierId>:<letterId|IL date>:<channel>`; `scheduled_at` per G-06 quiet hours (an owner tap at 23:30 goes out at 06:00; Friday 16:00 goes out after Shabbat). At most one letter and one reminder per supplier per Israel day.
   - The UI holds the send 10 s ("בטל שליחה", the shared deferred pattern) before calling the mutation.
   - Audit `claim.sent_by_server` `{supplierId, letterId?, claimIds, channel, outboxId, automationId:'A22'}`.
2. **Delivery truth (`claimComms.reconcile`, called on recovery page load and by `send` replies).** When the outbox row is `sent`: letter claims `claimed → letter_sent` via W2-10 `sendLetter` (or `transitionClaim` for a reminder: `last_reminder_at` stamped, no status change). When `failed` or `skipped_no_provider`: nothing moves; the row shows "לא נשלח · שלחו מהטלפון" with the pre-addressed hand-off. No claim is ever marked sent before the provider confirms.
3. **Reply capture (PR b).** `captureClaimReply(tx, {restaurantId, channel, sender, body, subject, messageId})`, called from the ingest pipeline **before** order capture, returns `handled: true` only when: the sender resolves to a supplier (`ingest_senders.supplier_id`, or equals a supplier's contact/reconciliation address) **and** that supplier has a claim in `letter_sent|acknowledged|disputed` or a server-sent reminder in the last 60 days. Otherwise the pipeline continues unchanged (order capture keeps working for staff).
   - Stores one `claim_replies` row: `body_excerpt` ≤1,000 chars, `tag`, `confidence`, `classifier 'rules'`, matched `claim_ids` (checked against the same restaurant), `proposed_status`.
   - Notifies the owner (and manager) once per reply via `notify()`: "<ספק> השיב על דרישת הזיכוי: 'נוציא זיכוי' · לאשר?" (₪ allowed: finance roles only).
4. **Classifier (`classify.ts`, pure, deterministic).** Tags:
   - `accepted` ("מאשר", "מקובל", "צודקים") → propose `acknowledged`
   - `credit_promised` ("נוציא זיכוי", "יצא זיכוי", "נזכה") → propose `acknowledged` + note "הספק הבטיח זיכוי"
   - `disputed` ("לא מקובל", "לא נכון", "סופק כפי שהוזמן") → propose `disputed`
   - `question`, `unrelated`, `unknown` → no proposal. Confidence < 0.8 → `unknown`. Negation-aware ("לא נוציא זיכוי" → disputed). It never proposes `credited` or `recovered`. An optional assistant classifier (`aiAssistant` flag, Ask infrastructure, server-side) may only raise or lower confidence of the same tags and writes `classifier 'assistant'`
   - no model name in code or copy.
5. **Confirm / dismiss (`claimComms.decideReply`, owner + manager).** `{replyId, decision: 'confirmed'|'dismissed', expectedStatuses, clientMutationId}`. Confirm runs the proposed transition per claim with `expectedStatus` (G-05 CONFLICT if it moved); dismiss changes nothing. Both stamp `decided_by/at` and audit `claim.reply_decided` (`automationId:'A22'`). A portal answer (H-06) arrives the same way with `classifier 'portal'`, confidence 1.0, and still needs confirm.
6. **Replies panel (`/dashboard/recovery/replies`).** Per supplier: latest replies (excerpt, channel icon, received time, tag chip), the proposal "לסמן כ'הספק אישר'?" with "אשרו" / "התעלמו", and the matched claims with ₪ via `<Money>`. Unknown replies read "תשובה מהספק · לא זוהתה כוונה" (T4 neutral). Owner, manager, bookkeeper read; receiver and chef forbidden (server).
7. **Send button (`SendToSupplierButton`).** On a ready letter and on an overdue supplier row: "שלחו לספק במייל" / "שלחו לספק בוואטסאפ" (shown only when allowed), the target address/number visible before the tap ("ל-orders@tnuva.co.il"), then the 10 s undo, then status chip "בשליחה" → "נשלח 12.01 09:14" or "לא נשלח · שלחו מהטלפון".
8. **Safety (server tests).** No outbox row targets a supplier without an owner-authenticated `send` call; no letter with an `open`/`escalated` claim can be sent; no MISSING_ON_INVOICE line in any supplier text; no reply ever changes `credited_agorot`, `recovered_at` or `credit_notes`.
9. **Off switch.** Option `supplierSend` gates `send` and the button; reply capture is gated by the same option plus H-13's table; off → `captureClaimReply` returns `handled:false`, the pipeline behaves exactly as today.
10. **Copy, he/en.** Supplier text in Hebrew whatever the UI locale (as W2-10); terms "דרישת זיכוי", "פער", "חשבונית זיכוי"; ₪ via `moneyText` in server text, `formatIls()` in UI; never "דליפה" to a supplier.

Where the docs conflict: IMPLEMENTATION-PLAN line 607 titles H-06 "Supplier claim portal **and server send**" and says the portal answer moves the status "automatically". **One owner for the supplier server-send primitive: H-06** (the human PR, public attack surface), as IMPLEMENTATION-PLAN and README §9/§10 already say. AU-17's `claimComms/send.ts` is the owner-tap mutation, target/opt-in checks, 10 s undo, audit and delivery-truth reconcile around **one call** to H-06's primitive; it does not build its own enqueue-to-supplier path. The owner rule makes every state change human-confirmed, so AU-17 treats a portal answer as a confirmed-on-tap proposal. If H-06 drops the send from its scope, the orchestrator records that in README §9 and IMPLEMENTATION-PLAN H-06 before AU-17 PR a takes the primitive over; until then the two documents agree on H-06.
