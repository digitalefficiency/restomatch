## 5. Acceptance criteria
1. **`address.ts`:** branded `Address = EmailAddress | VerifiedE164Phone | PushSubscriptionId`. Constructors validate (e-mail syntax; E.164 `+972…` only when `phoneVerifiedAt` is set; a push id only once H-03's table exists, so none today). `addressToTarget(a)` is the only path to the outbox `target` string. `@ts-expect-error` proves a plain `'role:manager'` string is not an `Address`; a runtime guard throws `INVALID_TARGET` on any target starting `role:`.
2. **`notify(tx, {event, audience, template, vars, deepLink, entity})`:** `audience` is `{userIds} | {roles} | {poSenderOf: poId} | {decidersOf: discrepancyId}`; it resolves at enqueue, inside the restaurant scope only, to **one outbox row per (user, channel)** with `dedupeKey = ${event}:${entity.id}:${userId}:${channel}` (a replay enqueues nothing) and `payload.{userId, event}`; channels follow the user's addresses (e-mail always; WhatsApp only with a verified phone); locale from `memberships.preferredLocale`. It only enqueues; it never calls an in-process `Notifier.send`.
3. **Owner alert rules, enforced now** (the spec defers cadence to H-05; the owner decision is binding, so it applies here):
   - quiet hours 23:00–06:00 and Shabbat (default window Friday 15:00 → Saturday 21:00, restaurant tz, `Asia/Jerusalem` fallback; a named constant H-05 may refine with holidays): `notify` sets the row's `scheduled_at` to the next allowed minute with one `UPDATE notifications_outbox SET scheduled_at = … WHERE id = … AND status = 'queued'` in the same `tx`. The dispatcher already claims only `scheduled_at <= now()`, so no dispatcher change is needed;
   - at most 6 per person per day: count today's rows for `payload.userId` (restaurant tz day); from the 7th, `scheduled_at` moves to the next allowed slot and `payload.digest = true` (H-05 folds these into one digest);
   - receiver and chef get no ₪ in any var (redacted by `money.view`; until G-07, by role).
   These are pure, unit-tested helpers in `notify.ts`.
4. **No lies:** rows without a provider stay `queued` until the dispatcher turns them into `failed + SKIPPED_NO_PROVIDER` (or `skipped` once G-03 deploys). After `matchInvoice`, `sendMonthlyReports` and an OCR failure on a test DB, new rows with `target LIKE 'role:%'` from your paths = **0**, and no row is `sent` without a provider id. (`matchInvoice`'s own `role:` rows disappear when W2-04 switches; the orchestrator's 0-check runs after both merge.)
5. **`reports/send.ts`:** the owner/manager audience goes through `notify()` for e-mail and WhatsApp; `MockWhatsAppNotifier` is no longer used here. `monthlyReports.sentAt` is set only by a reconcile step at the start of each run: `min(sent_at)` of this report's outbox rows with `status = 'sent'`, never at enqueue. Idempotency comes from the dedupe keys; a run that enqueues nothing new counts the restaurant as `skipped`. Per-tenant failure isolation unchanged.
6. **`ocrInvoice.ts`:** status writes go through G-05 invoice transitions (`ocr_parsed`). OCR **never writes `matched`** (row 144 becomes `parsed`); readers that mean "checked" use G-05's `INVOICE_CHECKED`. A terminal failure keeps `markOcrFailed`'s guard and payload, then emits `invoice.ocr_failed {invoiceId, uploaderId, reason}`: the notify effect reaches the uploader (no ₪) and the owner/manager members (with supplier and file); W2-08's task effect creates a T2 task. A retry or replay creates no second notice.
7. **`recipients.ts`:** `recipientsForRestaurant` unchanged (same rows, same order). New `resolveAudience(db, rid, audience)` → `{userId, role, locale, addresses: Address[]}`. Cross-tenant: an audience naming a user of restaurant B, resolved for A, yields 0 rows.
8. Demo ₪ invariants unchanged: no money path touched; the lab hero, pay-run and letters are identical before/after.
