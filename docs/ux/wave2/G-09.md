# G-09 · Multi-page documents on every intake path
**One line:** a 2–4-page invoice or a חשבונית מרכזת becomes ONE invoice with every page in OCR, whether it comes from the dock camera, e-mail or WhatsApp. Today page 2 never reaches the matcher, so its overcharges are missed and its PO lines look "missing from the invoice". A supplier's 2 WhatsApp photos of one invoice create 2 invoices, one without a number. This protects the page-2 ₪ and stops the false gaps that waste the owner's decision time. **Owner agent:** ocr-procurement-engineer (tenant-security-warden reviews the object-prefix checks). **Device:** both (server-only, no UI). **Effort:** M. **humanPR:** no.

## 4. What to fix and build
- **Findings:**
  - receiving-03: capture is one file, so page 2+ of a delivery invoice or חשבונית מרכזת never reaches the matcher (missed leak plus false "missing" lines);
  - mobile-field-04: one page only, so page 2+ of a consolidated invoice is lost, and the leak is under-counted on every intake path (dock, inbox upload, consolidated panel, share target).
- **Deep-fix class 3 · one document = one file.** The systemic fix:
  - a document is a page list; each page is uploaded separately, with its own id plus the document id, direct to storage;
  - the server composes ONE PDF for ONE invoice;
  - the same composer on every path (dock camera, offline queue, e-mail, WhatsApp). Images from one message, or from one sender within 10 minutes, are one document, with "פצלו";
  - retroactive repair: "צרפו כעמוד 2 לחשבונית X" merges an already-split invoice and runs OCR once;
  - store a storage path, never a 30-min signed URL.
  The retest corrections (DEEP-FIX §3): a re-shoot is a new file, so sha256 can't detect it; `page_count` is never saved today (the mapping-row bug); a server upload can exceed the 4.5 MB body cap; a PDF can't embed webp; WhatsApp/e-mail intake was in no package.
- **Part B ties (not built here):** W2-02's inbox "attach as page / split" calls you. W2-05 sends a per-page `clientPageId` plus a `clientDocumentId` composed via you. W3-11 later reuses you for credit-note and statement photos.

## 5. Acceptance criteria
1. **`documents/compose.ts`:** `composeDocument({restaurantId, clientDocumentId, pageObjects: string[]})`.
   - Every object must be a storage path under `${restaurantId}/` with no `..`; a foreign or traversal path → NOT_FOUND, with no existence oracle.
   - Only JPEG/PNG pages, sniffed by magic bytes, not the extension. Anything else → a named reason (`unsupported_page_type`, incl. webp: clients normalise to JPEG; W2-05 does it in `prepareScanFile`).
   - The pages are merged in array order into one PDF with `pdf-lib`, written at `${restaurantId}/${deterministicScanId(restaurantId, clientDocumentId)}.pdf`.
   - Idempotent: the same `clientDocumentId` → the same object; an existing object returns `{storagePath, pageCount, sha256}`, and pages are never re-read.
   - Over the 10 MB `attachmentBytes` → a named reason.
   - The per-page objects are deleted only **after** a successful write (best effort, logged).
   - It works in local dev storage (`saveLocalScan`/`readLocalScan`).
2. **`documents/objectRef.ts`:** `toObjectRef(rawImageUrlOrPath, restaurantId)` returns the tenant storage path for both legacy signed-URL rows and new path rows, and `signObjectRef` signs one for OCR. Use it for the dedupe key in `registerIngestedDocument` (instead of `split_part`) and store the **path** in new rows. W2-05 adopts the same helper in `registerInvoice`, so the two paths dedupe alike.
3. **One message → one document.**
   - In `processInboundMessage`, the JPEG/PNG image attachments of one message become ONE candidate document composed by the same helper.
   - Each PDF stays its own document.
   - Small inline images (e-mail signature logos, below a tested constant, e.g. < 20 KB or `Content-ID` inline) are not pages: record them `skipped` with the reason `inline_image`.
   - Every attachment keeps its own `ingest_documents` row, pointing to the one invoice.
4. **One sender within N minutes → one document.** A WhatsApp/e-mail image from the same normalised sender on the same channel within N minutes attaches as the next page of the open candidate. N is a restaurant setting, default 10, read with a local zod parser of `settings.ingest.groupMinutes`, because `RestaurantSettings` lives in immutable `schema.ts`.
   - "Open" means its invoice has no human decision, no claim, and is not approved or paid.
   - The composite is rebuilt at the same object, and the invoice is re-OCR'd at most once per added page (dedupe key `ocr:<invoiceId>:<pageCount>`).
   - Anything later starts a new document.
5. **Kept behaviour.** The identical-sha256 dedupe stays: the same bytes in a new message is a duplicate link, never a page and never a re-OCR (`ingest.attack.test.ts:457` stays green). A replay of the same provider message is a no-op (262). Unknown senders stay `needs_review` with no OCR spend, and grouping applies to their review card too. The quota logic is unchanged.
6. **Invoice creation** goes through G-05's invoice machine (`initial`), with no status literal. `invoice_scans` gets the **invoice uuid** plus `page_count` for ingested documents (the mapping row that fails today for `scan-…` ids).
7. **`documents/attach.ts`** (services for W2-02's procedures):
   - `attachAsPage({restaurantId, invoiceId, documentId, pageIndex})` merges an already-split second invoice into the first. It is refused with a named reason when the absorbed invoice has a decided פער, a claim, or is approved/paid. Otherwise one transaction retires the absorbed invoice through G-05, recomposes, and enqueues OCR **once**;
   - `splitDocument({restaurantId, invoiceId, pages: number[][]})` is the inverse: N invoices, each composed, OCR once each;
   - both are tenant-scoped (a foreign id → NOT_FOUND) and replay-safe (`withIdempotency` once G-05 merges).
8. **No ₪ change on existing data.** Only new intake behaves differently. The demo invariants are unchanged (hero ₪759.54, approvals 4 / ₪296.00, consolidated overcharge ₪36.00 excl. VAT). No backfill of old split invoices (decision 24: fixing existing bad data is read-only reports plus human approval, after the pilot).
