## 5. Acceptance criteria
1. The route `Body` is strict: `{ intent: 'as_ordered'|'with_changes', lines: [{ poLineId, qtyAvailable: number|null, proposedUnitPrice?: number|null }], note?: string|null }`. A missing or unknown intent → 422 (schema).
2. The service enforces the contract. **It is the authority; the route only maps codes.**
   - Every PO line exactly once: a missing line → `INCOMPLETE_ANSWER` (422 `incomplete_answer`). A foreign or duplicate line stays `BAD_LINE` (400 `invalid_lines`).
   - `with_changes`: every line needs a non-null `qtyAvailable` (0 = out of stock), otherwise `INCOMPLETE_ANSWER`. If there is no difference and no note → `INTENT_MISMATCH`. This is my reading of "contradictory"; state it in the PR.
   - `as_ordered`: `qtyAvailable` may be null or equal to the order. Any line whose qty or price differs → `INTENT_MISMATCH` (422 `intent_mismatch`).
   - `status` is still derived from the diff: no diff and no note → `confirmed`, otherwise `changes`. The stored `supplier_responses.lines` stays differences-only, so `supplierResponseDiff`, the order card and the demo diff are byte-identical.
3. `intent` is **optional in `SupplierAnswerInput` at the service type level only**, so the immutable `rls.attack.test.ts:789` still compiles and passes. When it's absent, it is inferred from the diff and marked `@deprecated` in JSDoc. `apps/web/lib/supplierConfirm/data.ts` (`supplierPortalSubmit`) takes a type where it is **required**.
4. The note is always carried, under both intents. A note with `as_ordered` → status `changes` (today's rule, kept).
5. A replay → 409 `{ ok:false, error:'already_answered', recorded:{ status, submittedAt, lines, note } }`, read through `supplierPortalView(token)` and never echoed from the request. The client compares it with `isOwnAnswer`: its own retry shows the done card with the recorded diff, and someone else's shows `RecordedNotice`. It is never a false success.
6. One pure `buildAnswer(state)` in `logic.ts` returns `{ intent, body, primary: 'invalid'|'as_ordered'|'with_changes', count, diff }`. The primary, the "אישור כפי שהוזמן" text button and the discard confirm all use it. `answerBody` and `primaryAction` are removed or become thin wrappers over it. The as-ordered path now sends **every line** with `qtyAvailable = qtyOrdered` and `intent: 'as_ordered'`. No `lines: []` is ever sent.
7. `supplierConfirm/expectation.ts` exports a pure `expectedQtyForLine(poLine: { id: string; qtyOrdered: number|string }, answer: { lines: SupplierResponseLine[] } | null): { qty: number; source: 'supplier'|'ordered' }`:
   - the supplier's `qtyAvailable` (0 stays 0) beats the ordered qty;
   - no answer, or no entry for the line → ordered.

   It imports no db and has JSDoc naming W2-05 and H-08 as consumers.
8. Callers are updated:
   - the demo seed answers every line with `intent: 'with_changes'`, and the stored diff equals today's (same 2 changes, same note);
   - `route.test.ts`: `{lines: []}` → 422 and nothing is stored;
   - `supplierConfirm.test.ts:147` is flipped the same way.

   Each flip asserts more, never less.
9. Parsing: drop the import from `contracts/logic.ts`. Qty and price use `parseNumberInput` (W1-10). `"0,250"` qty → 0.25; price `"1,250"` → 1,250. An invalid field always blocks; it never falls back to "as ordered".
