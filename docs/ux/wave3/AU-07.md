# AU-07 · Automation telemetry: measured minutes, zero-touch share and the ₪ funnel per restaurant
**One line:** the platform admin (and later the owner) sees, per restaurant per Israel week, how many documents came in, what share went through untouched, how long arrival → matched took, how old decisions get, which alerts led to an action, and where the ₪ stops on the way found → decided → claimed → sent → credited → recovered.
- **Why it matters:** it turns every research ASSUMPTION (60% claimable, ~35% collected, 3–5 min per document, 1–1.5 h/week saved) into a measured number within 30 days of the ציקטי pilot. It saves no hours and moves no ₪ by itself; it makes every other AU claim checkable.
- **Today:** nothing measures any of this, and no competitor publishes it either (ext-03 §0.1, ext-05 §1.3). The charts leak filter still counts MISSING_ON_INVOICE (`packages/charts/src/leak-views.ts:134-136`), so a naive funnel would inherit an inflated "found".
**Owner agent:** matching-engine-guardian owns the SQL (`packages/charts/src/automation.ts`); web-feature-engineer owns the procedure and the admin page (leak-economist signs every ₪ label and the time-ledger caveat; tenant-security-warden reviews the cross-tenant admin read). **Device:** desktop (admin console). **Effort:** M (2 PRs: a = charts SQL + tests, b = procedure + page). **humanPR:** no (read-only; no schema change; a missing column is proposed to H-13, never added).

## 5. Acceptance criteria
1. **`automationKpis(db, restaurantId, {weeks, now, rates?})`** in `packages/charts/src/automation.ts`, pure SQL reads, Israel weeks (Sunday 00:00 Asia/Jerusalem → next Sunday), `weeks` 1..12, returns one row per week:
   - `docsIn` (invoices by `created_at`, split by `source`), `inboxDocs` (`ingest_documents`), `duplicateCopies` (`raw.duplicateOf` set);
   - `zeroTouchPct` + `zeroTouchBasis: 'proxy'|'events'` (§3 rule), denominator = invoices first matched in the week, consolidated (`raw.kind='consolidated'`) and pending-link invoices excluded and counted apart (T4);
   - `arrivalToMatchedHoursP50/P90` (`invoices.created_at` → first `match_runs.run_at`);
   - `exceptionPct` (latest run has ≥1 warn/block finding other than UNORDERED_ARRIVAL pending link);
   - `decisionAgeHoursP50` (decided in week: `resolved_at − created_at`) and `openDecisionsOver24h` (count, now);
   - `alerts`: by event key (`payload.event`, else the `dedupe_key` prefix) → `{queued, sent, failedNoProvider, failed, opened: null, actedWithin48h}`; acted = the related entity (`related_entity_type/_id`) got a human decision or transition (`discrepancies.resolved_at`, `recovery_events` with `actor_id`, `audit_log` with `user_id`) within 48 h of `sent_at`;
   - `funnelAgorot` (integers): `found` (per-invoice capped leak via W2-09a, MISSING_ON_INVOICE excluded), `decided` (accepted, claimable types only, by `resolved_at`), `claimed` (`amount_agorot` by `claimed_at`), `sent` (by `letter_sent_at`), `credited` (`credited_agorot` by `credited_at`), `recovered` (by `recovered_at`); each stage dated by its own stamp (flow view) plus `cohort` = the same claims followed from their `claimed_at` week;
   - `automationRuns`: count per `automationId` (A1..A26) from `audit_log.after->>'automationId'` and `activity_events.metadata->>'automationId'`;
   - `flagsOn` (count of `FEATURE_KEYS` on, `FEATURES_OFF` applied).
2. **Time ledger, separate.** `timeLedger` = Σ per role of (documents × minutes-saved range × loaded rate).
   - `AUTOMATION_RATE_DEFAULTS` = receiver ₪63, bookkeeper ₪89, manager ₪103, chef ₪127, owner ₪150 per hour; minutes ranges from the catalogue §0; each labelled ASSUMPTION.
   - It returns `{lowIls, highIls, assumptions[]}` and is **never** added to any funnel figure (different result keys; a test asserts no field sums them).
   - Rates are overridable per request, not persisted (persistence = later settings jsonb, not a column).
3. **`admin.automationKpis`** (`adminProcedure`, query).
   - Input `{restaurantId: uuid, weeks: 1..12 default 8, rates?: Partial<Record<Role, number>>}`.
   - Reads only rows with `restaurant_id = input.restaurantId` (an explicit filter in every subquery).
   - Unknown restaurant → `NOT_FOUND`; non-admin → FORBIDDEN; no audit row (a read).
   - Coverage fragment `'admin.automationKpis': 'admin-denial'`.
4. **Page `/admin/automation?r=<id>&w=8`** (desktop ≥1280).
   - A restaurant picker (reuses `admin.listRestaurants`) and a week table (rows = weeks, columns = AC 1 metrics).
   - A funnel bar row per week; ₪ via `formatIls()` / `<Money>` only.
   - A "שווי זמן (הערכה)" card visibly apart from the ₪ funnel, with its assumptions listed and the caveat "עלות מנהלת חשבונות חיצונית יורדת רק אם התעריף יורד".
   - "לא נמדד" for opened alerts; a "הערכה" chip on proxy metrics; "אין עדיין נתונים" for weeks before the first event (never 0).
   - Light tokens, RTL, he/en parity, numbers right-aligned.
5. **Parity (money truth).** On the canary fixtures and the lab month:
   - Σ `found` over the month's weeks = `owner.leakHero` month leak − its MISSING_ON_INVOICE part, exactly, in agorot;
   - `claimed` = Σ `recovery_claims.amount_agorot` for the same window;

   - when H-07 lands, the MISSING_ON_INVOICE part is 0 and the test still passes (no edit needed).
6. **No schema, no write.** The diff has no migration; a test runs the procedure and asserts zero new rows in every table.
7. **Performance.** ≤ 800 ms for 12 weeks on the lab DB (one query per metric family, `EXPLAIN` shows index use on `invoices_restaurant_status_idx`, `notifications_related_idx`, `recovery_claims_restaurant_status_idx`); otherwise drop to 8 weeks max and say so.
