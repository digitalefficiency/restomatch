# G-15ʰ · Money engines: a typed basis per discrepancy, info-row routing, the pay-approval rule

**One line:** every discrepancy says *how* its ₪ was computed (ordered / received / billed / contract / unit price / VAT basis) in a typed `basis`, rows that are not leak are acknowledged with no ₪ before the cumulative rules, and "over ₪N or a new supplier → owner approves for payment" becomes one pure rule. **HUMAN-PR** (`packages/matching/**`, `approvals/engine.ts`).

## 4. Slices
- **A · basis (engine).** `Discrepancy.basis?: DiscrepancyBasis` (optional in the type so every other constructor of `Discrepancy` keeps compiling; the engine always sets it). Shape:
  `{ source: po|baseline_p90|gr|invoice_line|invoice_total|vat_rate|none, formula: price_x_qty|unit_x_qty|amount|amount_diff|none, qtyOrdered, qtyReceived, qtyBilled, qtyUsed, unitPriceUsed, referencePrice, unitFactor, overlapUnits, actualAmount, referenceAmount, vatRate, threshold{pct, abs, units} }` (nulls where not applicable). `basisDeltaAmount(basis)` recomputes the ₪ from the basis with the engine's own money helpers.
- **B · info-row routing.** A rule `non-leak-acknowledge` (priority 75: below the duplicate / no-PO / unordered / severity-block controls, above `cumulative-*`) catches every row the leak does not count at routing time (`severity = info`, `PRICE_LOWER`, `UNORDERED_ARRIVAL` that no control caught) → `requiredRole: null`, `action: auto_approve` (status `accepted`, ₪0 asked). Exported `countsAsLeak()` mirrors `LEAK_FILTER`'s routing-time part. Today an info row on a run with cumulative > ₪300 sits open in the owner queue.
- **C · pay-approval rule (decision 9).** Pure `evaluatePayApproval({ invoiceTotalInclVat, supplierPriorInvoices }, thresholds)` → `{ requiresOwner, reasons[] }`; `resolvePayApprovalThresholds(settings.approvalThresholds)` reads `payApprovalOverAmount` / `newSupplierInvoiceCount` read-only (no settings-router write path added). Defaults ₪5,000 and "first invoice" — **N is the owner's call**.
