# H-07ʰ · The monthly leak close: a snapshot on the 5th, dated corrections, a closed month never restates

## 5. Acceptance
1. **Close rule:** month M is closed from 00:00 on the 5th of M+1 in the restaurant's time zone. Before that the month is open and gets no snapshot.
2. **Snapshot:** version 1 per (restaurant, month), `leak_agorot` = the hero leak of that month **to the agora** (the job refuses to write when the per-invoice sum and `computeLeakHero` disagree), `reason` NULL, `created_by` NULL (system). Payload `leak-month-close/v1`: the hero fields in agorot, the time zone, the close instant, the basis note (pre-G-14 interim, M6), and the leak per invoice (agorot) as the correction baseline.
3. **Catch-up:** the first run snapshots every closed month from the restaurant's first invoice month (at most 24 months back) that has no snapshot. A second run writes nothing.
4. **Never restates:** a snapshot row is never updated (the 0072 trigger is the backstop; the job never issues UPDATE/DELETE). A human re-close is version n+1 with a reason; the job never writes version ≥ 2.
5. **Dated corrections:** on every run, for each closed month, the current leak per invoice is compared with the latest snapshot's baseline plus the corrections already written for that invoice; each non-zero difference becomes one `leak_month_corrections` row (signed `delta_agorot`, `entity_type='invoice'`, `entity_id`, a reason naming the recompute date, `created_at` = the date). Idempotent: an unchanged month writes nothing.
6. **Read model:** `readClosedLeakMonth` returns the frozen figure, the dated correction lines and their sum, never a restated total.
7. Per restaurant in one transaction under an advisory lock; one restaurant's failure does not stop the others (reported in the result).
8. No live ₪ figure moves: the hero, the reports and the canary are unchanged (signed before/after in the PR).
