# W3-07b · Team join and sign-in v2 (brief)

**One line:** an invitee opens `/join/<token>`, sees restaurant, role and inviter, proves the invited mailbox with a 6-digit e-mail code, sets their own name and password, and lands signed-in on `/welcome` → their role home. No PIN, no device mode: every worker signs in with their own e-mail and password.

## 4. Slices
- **a (this PR) — join + welcome + team links + onboarding detection**
  1. `/join/[token]` (public): states valid / expired / used / not-found (T4 calm). Valid shows restaurant, role label, inviter, masked invited address. Branches: (i) signed in as the invited address → "הצטרפות" accepts at once; (ii) the address already has a password → "התחברו כדי להצטרף" (login with the address prefilled, back to the accept page); (iii) new or password-less address → e-mail code flow.
  2. Code flow (server actions, owner auth connection, no tRPC): `sendJoinCode` — 6 digits via `crypto.randomInt`, HMAC-SHA256 with `AUTH_SECRET`, 10 min, a new code replaces the old one, limited per invite (3 / 15 min) and per IP (10 / 15 min) through `enforceRateLimit`; dev/e2e prints it and writes `JOIN_CODE_FILE`. `completeJoin` — reserve-then-count attempt markers (≤5 per code window), timing-safe compare, re-check the invite (pending, unexpired, same hash), then in one transaction: user (the invited address only, never a client-typed one), password (policy), membership with the invite's role and locale, invite → accepted, audit `team.invite_accepted`, codes and markers deleted. Then sign in through the existing Credentials provider (its own limiter + lockout + 2FA gate apply) → `/welcome`.
  3. `/welcome` (session): name, language (he / en; ar/ru/th/ti only when enabled), a short "add to home screen" coach (text only; the real install sheet is W3-03's), finish → `/dashboard` (role home).
  4. Team screen: invite / resend results show the `/join/<token>` link with "העתקת קישור" and "שליחה בוואטסאפ" (`wa.me` share). The invite e-mail links to `/join/<token>` once the publicPaths line is in; until then the old `/login?callbackUrl=/invite/accept…` link stays (interim).
  5. `/onboarding`: if the signed-in address has pending, unexpired invites, list them first ("הוזמנתם ל-X כ-Y · הצטרפות") so the user joins instead of creating a stray tenant; accept by invitation id, bound to the session's address.
- **b (later PR)** — sign-in v2: a 6-digit e-mail code on `/login` (same store, `one-time-code`, auto-submit), passkeys for owner + bookkeeper behind a flag via the existing `authenticators` table (needs the W3-03 dependency lane), remember-me pre-checked only in standalone display mode, QR for the join link (dependency lane).

## 5. Acceptance
- `/join/<token>` with a pending, unexpired token shows restaurant, role and inviter; expired, used, revoked and unknown tokens show calm states and never leak the restaurant.
- The token is single-use, 7-day, e-mail-bound: a second completion, a foreign session, or a different address cannot use it; the role comes only from the invitation.
- The code is 6 digits, valid 10 min, at most 5 wrong attempts (durable), never stored in clear, never logged in production.
- A completed join creates exactly one membership in the inviting restaurant and a signed-in session; the user lands on `/welcome`, then on the role home.
- `/onboarding` offers pending invites before "create a restaurant"; accepting one never works for an invite addressed to someone else.
- Hebrew-first RTL, AA pairs, partner wording; no ₪ anywhere in this package.
