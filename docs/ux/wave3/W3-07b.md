# W3-07b · Team join and sign-in v2 (brief)

**One line:** an invitee opens `/join/<token>`, sees restaurant, role and inviter, proves the invited mailbox with a 6-digit e-mail code, sets their own name and password, and lands signed-in on `/welcome` → their role home. No PIN, no device mode: every worker signs in with their own e-mail and password.

## 4. Slices
- **a (this PR) — join + welcome + team links + onboarding detection**
  1. `/join/[token]` (public): states valid / expired / used / not-found (T4 calm). Valid shows restaurant, role label, inviter, masked invited address. Branches: (i) signed in as the invited address → "הצטרפות" accepts at once; (ii) the address already has a password → "התחברו כדי להצטרף" (login with the address prefilled, back to the accept page); (iii) new or password-less address → e-mail code flow.
  2. Code flow (server actions, owner auth connection, no tRPC): `sendJoinCode` — 6 digits via `crypto.randomInt`, HMAC-SHA256 with `AUTH_SECRET`, 10 min, a new code replaces the old one, limited per invite (3 / 15 min) and per IP (10 / 15 min) through `enforceRateLimit`; dev/e2e prints it and writes `JOIN_CODE_FILE`. `completeJoin` — reserve-then-count attempt markers (≤5 per code window), timing-safe compare, re-check the invite (pending, unexpired, same hash), then in one transaction: user (the invited address only, never a client-typed one), password (policy), membership with the invite's role and locale, invite → accepted, audit `team.invite_accepted`, codes and markers deleted. Then sign in through the existing Credentials provider (its own limiter + lockout + 2FA gate apply) → `/welcome`.
  3. `/welcome` (session): name, language (he / en; ar/ru/th/ti only when enabled), a short "add to home screen" coach (text only; the real install sheet is W3-03's), finish → `/dashboard` (role home).
  4. Team screen: invite / resend results show the `/join/<token>` link with "העתקת קישור" and "שליחה בוואטסאפ" (`wa.me` share). The invite e-mail links to `/join/<token>` once the publicPaths line is in; until then the old `/login?callbackUrl=/invite/accept…` link stays (interim).
  5. `/onboarding`: if the signed-in address has pending, unexpired invites, list them first ("הוזמנתם ל-X כ-Y · הצטרפות") so the user joins instead of creating a stray tenant; accept by invitation id, bound to the session's address.
- **b (later PR)** — sign-in v2: a 6-digit e-mail code on `/login` (same store, `one-time-code`, auto-submit), passkeys for owner + bookkeeper behind a flag via the existing `authenticators` table (needs the W3-03 dependency lane), remember-me pre-checked only in standalone display mode, QR for the join link (dependency lane).

## 5. Acceptance
- `/join/<token>` with a pending, unexpired token shows restaurant, role and inviter; expired, used, revoked and unknown tokens show calm states and never leak the restaurant.
- The token is single-use, 7-day, e-mail-bound: a second completion, a foreign session, or a different address cannot use it; the role comes only from the invitation.
- The code is 6 digits, valid 10 min, at most 5 wrong attempts (durable), never stored in clear, never logged in production.
- A completed join creates exactly one membership in the inviting restaurant and a signed-in session; the user lands on `/welcome`, then on the role home.
- `/onboarding` offers pending invites before "create a restaurant"; accepting one never works for an invite addressed to someone else.
- Hebrew-first RTL, AA pairs, partner wording; no ₪ anywhere in this package.

## 8. Security review brief: /join account oracle + per-owner invite limit (post train D)
Branch `claude/w3-07b-join-oracle` (from main, with #309 merged in). The review diff is the two oracle commits on top of #309:
`git diff 2faefba9..HEAD -- . ':!apps/web/app/login' ':!apps/web/app/(auth)'` (7204e3da + 4d28943b; everything else on the branch is #309, reviewed already).

**Finding addressed (low, security review of /join).** A tenant owner could invite any address and read on the public `/join` page whether it already had a RestoMatch account. The page branched to "sign in" before any e-mail, and B5 (existing account means no code) made that more visible.

**What changed.**
- `app/join/[token]/page.tsx`: no account lookup. The first screen is the same for every valid invite: restaurant, role, inviter, masked address and "send me an e-mail".
- `app/join/actions.ts` `sendJoinCodeAction`: decides server-side, after the send step. A new address gets the 6-digit code. An existing account (any row, any canonical alias, with or without a password) gets `deliverJoinSignInLink`, a plain `/login?callbackUrl=/invite/accept?...` link with no code, no token and no password write. Both redirect to `?step=code&sent=1`.
- `joinFlow.issueJoinCode`: the per-address send cap (3 / 15 min, 10 / 24 h, durable) runs before the account check. An existing account returns `{ reason: 'hasPassword', throttled }`. When the address-wide cap trips, the action answers like a sent e-mail (`?step=code&sent=1`) and sends nothing. `e=rate` comes only from this invite's and this IP's limiters (review r1 finding 3).
- `joinFlow.completeJoin` (review r1 finding 1): attempt counters are split.
  - Per invitation (`join-fail-inv:` / `join-failtotal-inv:`; 5 per 10 min, 20 over the invite's life): every attempt is counted here, and these are the only counters an attempt with no live code touches.
  - Per address (B5; 5 per 10 min, 20 per 7 days): reserved only while a code is live, so each burst costs the mailbox an e-mail.
  - At a ceiling it answers `locked` and inserts nothing more.
  - `publicCompleteReason` folds `noCode` and `hasPassword` into `wrongCode`. So an existing account and a new address show the same answers and lock at the same attempt, and a token holder with no code can neither read nor spend the address budget in other restaurants.
- `packages/api/src/routers/team.ts`: `invite` and `resendInvite` (the two that send mail) share a per-owner `TEAM_INVITE_LIMIT` of 20 per hour. `revokeInvite` is never budgeted (review r1 finding 2) (prefix `team-invite-api`, durable `rate_limit_counters` on the owner connection, fails open like every limiter). It matches the web action's `INVITE_EMAIL_LIMIT`, and the prefixes are separate so the two never double-count. The immutable `api/trpc/[trpc]/route.ts` is untouched.
- Copy: the join step says "e-mail", not "code", so the text fits both outcomes.

**Invariants to check.**
1. No public response (page HTML, redirect URL, error key, lock point, send-cap point) differs between an existing account and a new address.
2. No path sets a password, name or `emailVerified` on an existing user row (B5 still holds).
3. The sign-in-link e-mail carries no code and no auth token; signing in still goes through the normal login (limiter, lockout, 2FA).
4. The unmasked address never reaches the client (`joinContact` is server-only).
5. `deliverJoinSignInLink` follows the r8 runtime rule: in a production runtime with no provider it throws and never logs.

- `app/join/__tests__/codeEmail.test.ts`: sign-in-link dev/production/send paths, plus mutation tests. Removing `production &&` or `env.RESEND_API_KEY` fails a test, for all three senders.

  - attempts past a lock add no markers.
- `e2e/W3-07b.spec.ts` (review r1): the address-wide send cap answers `sent=1` with no `e` and sends nothing.
- `e2e/W3-07b.spec.ts`: the `/join` `main` text is identical for an existing account and a new address before and after "send", and so is the redirect query. Server-side, the existing account got a link and the new address a code.

**Known limits (accepted, say if not).**
- Timing: the existing-account path skips the code insert and sends a different e-mail. The send happens in the action before the redirect, so the response time can differ by one DB write. The code path keeps the same statement shape where it matters (attempt counting).
- The sign-in link is a plain login link, not a magic link: an invitee with a passwordless account uses the normal e-mail-link sign-in from `/login`.
- B5's own assertions (on main) still expect `locked` from the address counters once a code is live, so the address ceiling stays visible after a send, as in the base. Before any send it is unreachable.
- `TEAM_INVITE_LIMIT` fails open on a counter-store outage (the same policy as `lib/rateLimit.ts`). The durable per-address caps in joinFlow do not fail open.
