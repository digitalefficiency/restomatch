# W3-09 · Order-to-door loop: PO lifecycle, supplier portal 2.0, document flow (+ AU-11 order autopilot addendum)

**One line:** a purchase order moves through one transition table fired by events (sent → confirmed by the supplier → partial / closed by receiving), the supplier answers per line in a 10-minute-editable portal in he/ar/ru, every PO / GR / invoice shows its document flow, and (AU-11) a prepared draft, a backorder draft and a failed-send rescue are waiting for a human. **Nothing is ever sent to a supplier automatically.**

## 5. Acceptance
1. One transition table; an illegal transition is refused; every applied transition is reported for `activity_events` + a sender notice (wired in b).
2. "late" is derived (expected + 60 min), never stored.
3. Portal 2.0: a line is ✓, a shortage (0 ≤ qty < ordered) or a substitution (product name + price > 0); window confirm or a proposal with start < end; an answer is editable for 10 minutes after submit, then locked; locales he/ar/ru, default he.
4. Prepared draft: one per supplier per order day (`au:A16:<supplierId>:<YYYY-MM-DD>`), ≤ 40 lines, prices only from the expected-price resolver (never the invoice), skipped for an inactive supplier, < 2 guide rows, an open human draft or a PO today. Never placed; no outbox row.
5. Backorder: never re-orders units the supplier billed (they belong to a credit request); one draft per GR (`au:A16b:<grId>`); nothing when every short line is excluded.
6. Send rescue: reads the send state only; never retries.
7. Every notice is ₪-free (no `₪`, no 2-decimal number) and uses partner wording (GLOSSARY §2): no דרישה / תביעה / מחלוקת / חוב / באיחור.
8. Receiver: FORBIDDEN on the new procedures, no notice (b).
