# WA-03ʰ · Schema + RLS for the agent: bindings, conversations, staged actions, message log, sender resolver
**One line:** four tenant tables and one `SECURITY DEFINER` function give the agent a place to remember **who** a WhatsApp number is (a verified, opted-in member in one restaurant and role), **where** the conversation stands (24-hour window, flow cursor), **what** a button may commit (a single-use, amount-specific token) and **what** was sent and delivered. Everything is under RLS, with add-only attack probes.

Today:
- nothing maps a WhatsApp `from` number to a person: `users.phone` (`packages/db/src/schema.ts:181`) has no writer and no verification; the intake allow-list `ingest_senders` (`schema.ts:1353`) is "a phone that may send invoices", with no user and no role;
- the only pre-tenant lookup is `app.ingest_resolve_channel(token_hash)` (`packages/db/drizzle/0050_ingest.sql:109-124`, `SECURITY DEFINER`, `REVOKE … FROM PUBLIC`, `GRANT EXECUTE … TO restomatch_app`), keyed on a URL token, one restaurant per channel;
- `memberships` (`schema.ts:249`) is keyed (user, restaurant, **role**), so one person may hold several roles and restaurants;
- there is no idempotency table (G-03ʰ adds `idempotency_keys`), no `phone_verified_at` (G-03ʰ) and no `whatsapp_opt_in` / `notification_prefs` (H-03ʰ).

## 4. What to build (the proposal)
- **`wa_bindings`**: `id`, `restaurant_id`, `user_id`, `roles user_role[]` (snapshot from `memberships` at verify), `active_role`, `phone_hash` (HMAC-SHA256 with a rotatable server pepper over **strict E.164**, not `waPhone()`; unique on `(phone_hash, restaurant_id) WHERE revoked_at IS NULL`, so one phone can hold one active binding **per restaurant**), `phone_last4`, `verified_at`, `opt_in_at` + `opt_in_notice_version` (stored per binding), `source` ('web_code'), `revoked_at`, `revoked_reason`, `suspended_at`, `created_at`. No plain phone column (the phone lives on `users`, G-03ʰ/W2-14). The hash is personal data with its own retention (WD9) and is deleted with the binding by the DSR job; it is not "kept for audit only".
- **`wa_link_codes`** (or a `kind` on `wa_staged_actions`; the human chooses): `code_hash`, `user_id`, `restaurant_id`, `expires_at` (10 min), `used_at`.
- **`wa_conversations`**: one per binding; `last_inbound_at` (24-h window), `active_restaurant_id`, `active_role`, `flow_state jsonb` (≤4 KB, 24-h TTL), `updated_at`.
- **`wa_staged_actions`**: `id`, `restaurant_id`, `binding_id`, `kind` (enum of WA-07's proposal kinds), `payload jsonb`, `payload_hash`, `amount_agorot bigint` (server-computed, nullable for no-money actions), `token_hash` (unique), `status` (staged/committed/expired/cancelled/undone), `expires_at` (30 min), `idempotency_key` (`wa:<wamid>`), `committed_at`, `undo_until`.
- **`wa_messages`**: `id`, `restaurant_id`, `binding_id`, `direction`, `wamid` (**unique**), `kind` (text/template/interactive/media/status/system), `template_name`, `status` (queued/sent/delivered/read/failed/skipped_no_provider), `error_code`, `cost_category` (utility/service/none), `outbox_id`, `created_at`. **No message text** (text lives 30 days in a separate nullable `text_redacted` column dropped by retention, WD9).
- **RLS:** every tenant table (four, or five if the human picks a separate `wa_link_codes`) `ENABLE ROW LEVEL SECURITY` with `restaurant_id = app.current_restaurant_id()`; bindings additionally readable by the owner and the bound user only (policy on `app.current_user_id()`), never by other staff.
- **Resolver:** `app.wa_resolve_sender(p_phone_hash text) RETURNS TABLE(binding_id, status)` `SECURITY DEFINER`, `STABLE`, fixed `search_path`, `REVOKE ALL FROM PUBLIC`; **revoke `EXECUTE` from `restomatch_app` after the `rls.ts:192` blanket grant** and grant it to a dedicated webhook role. It returns only the caller's own active bindings (one row per restaurant), ids and status only; the webhook then loads the binding **under the tenant GUC** (`withRestaurant`). Returns **0 rows** when the hash matches a supplier number (`ingest_senders.supplier_id IS NOT NULL` or `suppliers.contact_whatsapp`). "החלף מסעדה" picks among the caller's own bindings. Each restaurant's owner lists and revokes only their own restaurant's row.
- **Dedupe:** a **non-tenant** table keyed on `(wamid, kind[, status])`, written through a `SECURITY DEFINER` function; status callbacks update the outbound `wa_messages` row.
- **Retention hooks:** indexes on `created_at` for the WD9 sweeps (text 30 days, traces/media 90, outbound log 13 months).
- **Indexes (proposal):**
  - `wa_bindings (phone_hash, restaurant_id) WHERE revoked_at IS NULL` unique;
  - `wa_bindings (restaurant_id, user_id)`;
  - `wa_conversations (binding_id)` unique;
  - `wa_staged_actions (token_hash)` unique, `(status, expires_at)` for the sweep;
  - `wa_messages (wamid)` unique, `(restaurant_id, created_at)` for the cost meter and retention.
- **Owner decisions applied:**
  - identity is a member record, never a WhatsApp id (design §C.1);
  - money in integer agorot, computed by the server;
  - retention per WD9, with nullable text columns;
  - no staff-monitoring columns (no per-person response-time score).

## 5. Acceptance criteria
1. **Tenant isolation:** with GUC = restaurant A, raw SQL under the app role sees 0 rows of B in each of the five tables (add-only probes in `rls.attack.test.ts`).
2. **Bindings are private:** a manager of A cannot select another staff member's binding; the owner of A can; the bound user can (probe).
3. **No writes on `users`** remain revoked (existing `:201` assertion untouched and green).
4. **Resolver:** returns exactly one row for a single active binding; 0 rows for an unknown hash, a supplier number, two active bindings on one hash, a revoked or suspended binding; executable by the app role, not by `PUBLIC` (probe).
5. **`wamid` unique** and **`token_hash` unique**: a duplicate insert fails (shape test).
6. **Amount in agorot:** `amount_agorot` is `bigint`; no `numeric` ₪ column in these tables.
7. **Migration hygiene:** new file only; `drizzle-kit check` clean; `pnpm --filter @restomatch/db migrate` from empty applies 0000..new without error; canary green.
8. **COVERAGE untouched** (no procedure added here).

## 8. Notes + Traps
- **Trap:** storing the phone in plain text in a second place. Keep a hash (+ last 4 for display); the E.164 phone lives on `users` only.
- **Trap:** a resolver that "picks the first" binding when a phone is bound in two restaurants. It returns all of the caller's own active bindings; the conversation's `active_restaurant_id` ("החלף מסעדה") picks one, and a role change or removal at restaurant B kills only the B context.
- **Trap:** the app role. Agent turns run on the app-role connection; the owner connection appears only inside named `SECURITY DEFINER` functions. Probe: `current_user = restomatch_app` in a tool call.
- **Probes (add-only):** a role change or removal on restaurant B kills the B context but not A; B's owner can disconnect the B binding and cannot see A's; `restomatch_app` cannot `EXECUTE` the resolver.
- **Trap:** supplier numbers. The resolver must check suppliers **before** returning a staff binding (design §B.6 S3): a supplier must never open a staff session, even if a staff member mistakenly registered that number.
- **Trap:** the worker connects with an RLS-bypassing role (`rls/0002` header). WA-06ʰ's dispatcher and WA-11's sweeps must keep explicit `restaurant_id` guards.
- **Trap:** `roles user_role[]` snapshot drift. A membership or role change must revoke the binding (WA-04 enforces it; the schema just keeps `revoked_reason`).
- **Retention:** WD9 is the default; the lawyer (WA-12ʰ) may shorten it. Columns are nullable so retention can null text without deleting the audit trail.
- No personal ID number, bank detail or one-time code is ever stored in these tables.
- **Trap:** `flow_state jsonb` can grow into a chat memory. Cap it (≤4 KB), give it a 24-h TTL, and keep anything worth remembering as a real row (decision, draft, binding).
- **Trap:** `ON DELETE CASCADE` from `users` would erase audit context. Revocation is a status; DSR deletion of conversation rows is an explicit job (design §C.5), not a cascade.
- **Review checklist for the human:** five tables have `restaurant_id NOT NULL`; RLS enabled on each; the resolver is `STABLE SECURITY DEFINER` with a fixed `search_path`; `EXECUTE` granted to the app role only; no new grant on `users`; probes are add-only; `meta/` journal updated; backup taken before the 2.2 merge.
