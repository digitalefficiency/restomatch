# WA-04 · Phone onboarding: a person connects their own WhatsApp from a signed-in web session
**One line:** signed in on the web, a person taps "חבר את הוואטסאפ שלי", reads the AI notice, and sends a prefilled `wa.me` code from their own phone. The binding is accepted only when the code is valid **and** the sender equals their verified profile phone **and** the number is not a supplier's or someone else's. They start in their least-privileged role, can switch restaurant or role from a list, stop with "עצור", and the owner sees and disconnects connected phones on the web.

Today:
- `users.phone` (`packages/db/src/schema.ts:181`) has no writer and no verification; it is read only by DSR export (`routers/dsr.ts:89`) and the order document contact (`routers/orders.ts:276`);
- the app role cannot write `users` (`packages/db/src/rls.ts:201`), so a phone write must use the owner/auth connection scoped to the session user (the `dsr.ts` adminDb pattern, header `:45-51`);
- one person can hold several (restaurant, role) memberships (`schema.ts:249`), and the web session has one active role (`packages/api/src/context.ts:3-17`);
- role and member changes happen in `routers/team.ts` (`updateMemberRole` `:297`, `removeMember` `:346`, both `ownerProcedure`), with no hook for channel bindings.

## 4. What to build
- **Code mint** (`createLinkCode`, memberProcedure, feature `whatsappAgent`): requires a verified phone; returns `wa.me/<RestoMatch number>?text=חיבור RM-XXXXXXXX` (8 chars, Crockford base32, 10-min expiry, stored hashed, bound to user + restaurant) and a QR (rendered client-side). Rate limit 5 codes/hour/user.
- **Bind** (`bind.ts`, called by WA-05ʰ on an inbound text matching `^חיבור RM-[0-9A-Z]{8}$`): accept only if (a) code valid and unused, (b) sender E.164 = `users.phone` with `phone_verified_at` set, (c) `app.wa_resolve_sender` finds no supplier and no other active binding for that number. On success: binding row (roles snapshot from `memberships`, `active_role` = least-privileged, notice version), `users.whatsapp_opt_in` via the owner connection, welcome + AI disclosure reply. On failure: one fixed reply ("לא הצלחנו לחבר. בדקו באפליקציה שהמספר בפרופיל זהה לזה שממנו שלחתם.") and an in-app notice to the owner; no detail of which check failed.
- **Least privilege order:** receiver < chef < bookkeeper < manager < owner. "החלף תפקיד" / "החלף מסעדה" → list message of the person's memberships; each switch logged and shown in the next reply header ("ביסטרו הכרמל · מנהל").
- **Stop:** "עצור" → binding `revoked_at`, `whatsapp_opt_in = false`, one confirmation "הפסקנו. לא נשלח לכם יותר הודעות. לחיבור מחדש: האפליקציה." Nothing else is sent afterwards.
- **Revoke hooks:** role change, member removal, owner "נתק", a Meta "number changed" system event (from WA-05ʰ), 30 days without inbound → revoke with reason.
- **Re-verify:** every 90 days (ASSUMPTION) the binding goes `suspended` and WA-06ʰ's `rm_reverify` template is enqueued once; the person repeats the code flow.
- **Suspicion rules (design §C.1):** a burst of ≥5 decisions in 2 minutes, a request for exports or "all invoices", or a decision above half the WD2 limit from a binding re-verified <24 h ago → `suspended_at` + owner notice; re-confirm on the web.
- **Identity API for other packages** (`agent/identity/index.ts`):
  - `bindFromCode(sender, code)` (WA-05ʰ);
  - `activeContext(bindingId)` → `{ userId, restaurantId, role }` (WA-02's caller);
  - `switchContext(bindingId, restaurantId, role)` (WA-02's "החלף" commands);
  - `stop(bindingId)`, `revokeBindingsFor(userId, restaurantId, reason)`, `suspend(bindingId, reason)` (WA-07's suspicion rule, WA-11).
- **Owner decisions applied:**
  - every money action still needs WA-07's token tap: a binding alone authorises nothing;
  - no binding, role or recipient change from WhatsApp (never list item 3): connect and role changes are web-only;
  - the AI disclosure is shown before the code and in the first reply;
  - WD6 rollout: bindings of chef and receiver roles are refused until WA-09/WA-10's options are on.
- **Web page** (PR b): notice (design §C.6), button "חבר את הוואטסאפ שלי", QR + link, status ("מחובר מ-05.11 · ‎…1234"), "נתק". Owner view: connected phones per member (name, role, last 4 digits, since, last activity) + "נתק". Tips: two-step verification on the phone.

## 5. Acceptance criteria
1. **Two factors at once.** A valid code from a different number than the verified profile phone is refused; a correct number with an expired, used or other-user code is refused (tests per case).
2. **No code is ever sent to the phone** (test: 0 outbox rows of kind template/text containing `RM-`).
3. **Supplier numbers never bind:** a number in `ingest_senders` with a supplier, or equal to any `suppliers.contact_whatsapp`, is refused.
4. **One active binding per number**; a second user's code from the same number is refused and the owner is told in-app.
5. **Least privilege:** a person who is manager and chef starts as chef; "החלף תפקיד" lists both; the header line shows the active role after the switch.
6. **Revocation is automatic** on `updateMemberRole`, `removeMember`, owner "נתק", and the number-changed event; the next inbound from that number gets the unknown-number reply and no model call.
7. **"עצור" works in one message**, sets opt-in false, and no proactive message is enqueued for that user afterwards (test with WA-06ʰ's enqueue stub).
8. **Notice shown before the code and repeated in the first reply**, with the version stored; Hebrew text = design §C.6 until the lawyer's version replaces it.
9. **Privacy:** the owner list shows only the last 4 digits; no phone in logs or `activity_events`; no personal ID number anywhere.
10. **Off switch:** with `whatsappAgent` off the section is hidden and `createLinkCode` returns FORBIDDEN; `bind.ts` refuses.
11. **Web (PR b):** RTL, WCAG AA, keyboard reachable, he-IL dates; 390 px and desktop screenshots; axe clean.

## 8. Notes + Traps
- **Trap:** trusting the WhatsApp `from` as identity. It only names the chat; the binding row is the identity. Business-scoped user ids may replace phones in webhooks (UNVERIFIED): key on the binding, store the provider id when present.
- **Trap:** writing `users` with the app role. It is revoked; use W2-14's owner-connection writer for `whatsapp_opt_in` too.
- **Trap:** a binding that "follows" a role change. It never does: revoke and re-verify.
- **Trap:** leaking which check failed at bind time helps an attacker. One generic reply; details only in the owner's in-app notice.
- **Trap:** an authentication template. Not needed: the person writes first (inbound is free), and no code goes to the phone.
- **Trap:** QR codes leak the code to anyone who sees the screen. The code alone is useless without the verified phone (factor b), and it expires in 10 minutes and is single-use.
- The 90-day and 30-day periods are ASSUMPTIONS to revisit after E4.
