## 4. What to build (the proposal)
1. **Message kinds** on the outbox row: `payload.wa = { kind: 'text' } | { kind: 'template', name, lang: 'he', vars[] } | { kind: 'interactive', buttons[] | list | cta }`. `WhatsAppCloudNotifier.dispatch` sends all three; `send()` no longer dispatches in-process (the dispatcher is the only sender).
2. **Role → member phone at enqueue** (H-05) restricted to **verified, opted-in, non-revoked** WA bindings; no `role:` string ever reaches Meta.
3. **Status write-back** API `recordWaStatus(wamid, status, errorCode)` for WA-05ʰ; mocks write `skipped_no_provider`, never `sent`.
4. **Window tracker** (`window.ts`): `text`/`interactive` require `last_inbound_at` within 24 h at enqueue **and** at dispatch; otherwise refused (`refused: window_closed`) and, for T2, re-enqueued as the matching template.
5. **Cap accounting:** only `payload.proactive = true` rows count toward ≤6/person/day and quiet hours; replies are metered (`whatsapp_sends`, `cost_category`) but not capped here (WA-02 caps model turns).
6. **Template registry** (`whatsappTemplates.ts`): the 11 templates of design §D.6 with `{ name, roles[], vars[] (with a ₪ flag), buttons, category: 'utility' }`. Enqueue refuses a template whose `roles` excludes the binding's active role, and any ₪ var for receiver/chef templates (registry test: `rm_receiver_day`, `rm_receiver_late`, `rm_order_cutoff`, `rm_confirm_reply` have no ₪ var).
7. **Ops webhooks:** `template_category_update` (utility → marketing) pauses that template and alerts a human; `phone_number_quality_update` below GREEN alerts.
8. **`cron.ts` lines:** `wa-owner-brief` `30 7 * * 0-5` (Sun–Fri 07:30 IL, WD5; the job body is WA-08's) and `wa-sweep` every 5 min (expire staged actions, close stale `flow_state`) — or the sweep rides `outbox-dispatch`. The 7-day claim-overdue nudge rides AU-03's 08:30 run (no new line).
9. **Fallback (design §D.10):** a T2 row that fails (error, 131048, 368) or has no `delivered` within 15 min gets sibling rows on push and (owner/bookkeeper) e-mail; each channel recorded separately; WhatsApp is never the only channel.

## 5. Acceptance criteria
1. **No `role:` target** reaches `dispatch` (test over every producer: match alert, monthly report, briefs).
2. **Role-checked templates:** enqueueing `rm_owner_brief` to a receiver binding throws `template_role_mismatch`; a receiver template with a ₪ var fails the registry test.
3. **Window:** a free-form reply 25 h after the last inbound is refused at enqueue; a T2 falls back to its template.
4. **Cap:** 6 proactive templates to one person in an Israel day → the 7th is digested/deferred per G-06; 20 in-window replies the same day are not blocked here.
5. **Quiet hours/Shabbat:** a proactive template at 23:30 is scheduled for 06:00; Friday 19:00 → after Shabbat; replies to a person who wrote at 23:30 are allowed (WD4).
6. **Single sender:** `WhatsAppCloudNotifier.send()` only enqueues; a race test with the dispatcher yields one `dispatch` call.
7. **Honest mocks:** with no credentials rows end `failed + skipped_no_provider`, never `sent`.
8. **Status write-back:** `delivered`/`read`/`failed` update the row; `failed` with 131048 triggers the T2 fallback.
9. **Cron pinned tests** grow add-only with the two lines; existing schedules unchanged; `tz: Asia/Jerusalem`.
10. **Category flip** pauses the template within one webhook and creates an ops alert.
