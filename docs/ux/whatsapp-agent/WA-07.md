# WA-07 · Money actions over WhatsApp (hands): stage, confirm the exact ₪, commit once, undo for 10 minutes
**One line:** when the model proposes "claim this gap" or "waive it", the server checks the row, the tenant, the role and `requiredRole`, **computes the ₪ itself**, stores a single-use staged action and sends a button titled with the exact amount ("אשר 96 ₪"). Only that button, tapped from the same binding within 30 minutes on an unchanged row, runs the **real** mutation, once, under `withIdempotency` keyed on the tap's `wamid`, with an audit row `source: 'whatsapp'`. The "done" message is built from the committed row and offers a 10-minute undo. Amounts above the owner's WhatsApp limit go to the web app instead.

## 4. What to build
- **Stage** (`stage.ts`): input = a typed proposal from WA-02's registry (`approve_gap{discrepancyId}`, `waive_gap{discrepancyId, reasonCode}`, `mark_letter_sent{claimId}`, …). Validate tenant, binding role, `ensureCanAct` semantics (read via the caller's `myQueue`), and the never list. Compute `amount_agorot` from the row (`|deltaAmount|` parsed at the boundary to integer agorot); refuse NEVER_CLAIMABLE types for `approve_gap` ("שורה זו אינה ניתנת לבקשת הזיכוי."). Store token hash, payload hash, 30-min expiry. Send the confirm (interactive) through WA-06ʰ.
- **Confirm text (design §B.1):** "לבקש זיכוי של **96 ₪** מירקות השרון על חשבונית 20931?" buttons `[אשר 96 ₪] [ביטול]`; waive: reason list (`WAIVE_REASON_CODES` labels) then `[אשר כפי שחויב 96 ₪] [ביטול]`. ₪ via `moneyText`; button title ≤20 chars (fallback "אשר" + amount in body when longer).
- **Commit** (`commit.ts`): claim the token with `UPDATE wa_staged_actions SET status='committing' WHERE id=$1 AND status='staged' AND expires_at > now() RETURNING …`; re-run `activeContext()` (binding, membership, phone, `tokenVersion`) in the same transaction; recompute the payload hash over `(id, type, deltaAmount, status, requiresRole, match_run_id)` and refuse on mismatch; the tap's `context.id` must equal the outbound wamid that carried the token; then call the **real** procedure (`approvals.approve` / `reject` with `channel: 'quick'`) through the server caller inside `withIdempotency({ key: 'wa:<wamid>', procedure })`; mark the staged row `committed`; audit row `{ source: 'whatsapp', stagedActionId, bindingId, role, amountAgorot, before, after }`.
- **Done text** built from the committed row: "נרשם: 96 ₪ נוספו לבקשת הזיכוי מול ירקות השרון. אפשר לבטל עד 07:52." `[בטל] [הפער הבא]`.
- **Undo** (`undo.ts`): `[בטל]` within 10 minutes → `approvals.reopen` (WhatsApp window), audit `source: 'whatsapp'`, "בוטל. הפער חזר לרשימה."
- **Limits** (`limits.ts`, WD2 decided): a button only when the role passes `requiredRole`, claimable ₪ ≤ W2-04's `ONE_TAP_APPROVE_CAP_AGOROT` (₪500), not a block and not bulk; otherwise no token and a CTA "לאישור באפליקציה" to the go-link. The server re-checks at commit and refuses > ₪500 or a block even with a valid token. A waive that releases an invoice (`payRun.ts:14-23`) shows the released invoice total in the confirm (owner OK pending: cap on max(gap, released invoice)). `approve_unknown_document` and DUPLICATE "not a duplicate" are web-only in v1. Daily totals wait for WD11. Per-restaurant AU-01 options (web-only to change).
- **Kinds and their bar (design §C.2 proposal column):**
  - money, two taps + amount-named confirm: `approve_gap`, `waive_gap`;
  - no money, one tap, logged: `mark_letter_sent`, `postpone_delivery`, `create_order_draft`, `edit_order_line`, `cancel_draft`, `create_confirm_link`, `start_receipt`, `mark_gr_line`, `submit_receipt`;
  - never (no kind exists): pay run, mark paid, bulk release, bank details, staff/roles/bindings, deletes, allow-list, exports, plan/billing, automation rules, supplier send from our number.
- **Owner decisions applied:**
  - every money action is human-confirmed (two taps, the amount named on the button);
  - owner rules that lower the bar stay web-configured (AU-01/H-12); default always "confirm";
  - MISSING_ON_INVOICE is never claimable;
  - WD2 (decided): ₪500 per item, never block, never bulk; AU-01 overrides may only lower it; WD3 undo 10 minutes.
- **Step-up also for:** bulk ("תאשר הכל" → "אפשר לאשר באפליקציה, אחד אחד או בבחירה."), a binding re-verified < 24 h ago above half the cap (→ WA-04 suspension).

## 5. Acceptance criteria
1. **No commit without a token tap:** the model output "אושר" or a free-text "כן" changes nothing (test: approval state unchanged, 0 audit rows).
2. **Amount-specific:** the button title and body show the server-computed ₪; a tampered button id (other amount, other discrepancy, other binding) is refused "הכפתור הזה כבר לא בתוקף."
3. **Single use + idempotent:** the same tap delivered twice, two taps in parallel, or a replayed webhook → exactly one decision and one audit row (race test on the concurrency harness).
4. **Expiry:** a tap after 30 minutes → "פג תוקף האישור. פתחו את הפער מחדש." and nothing commits; WA-06ʰ's sweep marks it `expired`.
5. **Row changed:** a gap decided on the web after staging → `decidedConflict` → "הפער כבר טופל באפליקציה." no second effect.
6. **Role and `requiredRole`:** a manager's tap on an owner-required gap is refused; a chef or receiver binding cannot stage `approve_gap`/`waive_gap` (registry + server check).
7. **MISSING_ON_INVOICE / PRICE_LOWER / UNORDERED_ARRIVAL** are never staged as claims.
8. **Limits (WD2):** ₪500.00 → button; ₪500.01 → CTA, no token; a forged token on a ₪500.01 item → the server refuses; a block → CTA; a manager on an owner-routed item → CTA; an AU-01 override that raises the cap → ignored; a WhatsApp approve + undo within 10 min → succeeds (the reopen audit check passes).
9. **Undo:** 10 min for WhatsApp-originated decisions only; web decisions keep 15 s (existing tests unchanged).
10. **Audit:** the decision audit row itself carries `ctx.channel = { source: 'whatsapp', stagedActionId }` plus binding id, role, agorot, before/after (no separate row ahead of it); append-only.
11. **Off switch:** feature off → staging refused with the off reply; no staged rows created.

## 8. Notes + Traps
- **Trap:** computing ₪ from the model's proposal. The proposal carries ids only; the amount comes from the row at stage time and is re-checked at commit.
- **Trap:** money in shekel floats. `deltaAmount` is a NUMERIC string; parse to integer agorot at the boundary; never `parseFloat` for comparisons with the cap.
- **Trap:** the button id. Meta echoes it back: put only the opaque token there, never ids or amounts.
- **Trap:** idempotency keyed on the staged id alone lets a second tap of a re-staged action through; key on the tap's `wamid` **and** mark the staged row single-use.
- **Trap:** a staged action that outlives a role change. WA-04 revokes the binding; the commit must re-check the binding is active, not only the token.
- **Trap:** the "done" text. Build it from the committed row (amount, supplier, invoice) after the transaction, never from the staged payload (Instinct lesson, design §C.3).
- **Trap:** `approvals.ts` is W3-01's in wave 3. Do not touch it until the grant; the interim is the 15-s undo.
- Owner rules that lower the bar (auto-approve under ₪20) are AU-01/H-12 territory and web-configured; WhatsApp never changes them (never list item 9).
